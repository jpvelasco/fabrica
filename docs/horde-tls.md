# Horde TLS

Horde can use one HTTPS port for its web UI, REST API and agent gRPC. The
operator supplies a certificate, an unencrypted PEM key, a CA bundle and private
DNS. Fabrica configures listeners and clients; certificate issuance, delivery,
DNS records and renewal remain operator responsibilities.

TLS requires the Docker coordinator runtime generated by the updated
`fabrica horde ami build`, and native Linux stock agents. Validate your exact
server image and agent version with the smoke checks below before production
use. Native coordinator and Docker-agent TLS are outside this contract.

## Configuration and trust

```yaml
horde:
  port: 5000
  tls:
    enabled: true
    serverName: horde.example.internal
    certPath: /etc/horde/tls/server.crt
    keyPath: /etc/horde/tls/server.key
    caPath: /etc/horde/tls/ca-bundle.pem
  clientCAPath: ./certs/horde-ca.pem
  agents:
    caPath: /etc/horde/tls/ca-bundle.pem
ci:
  hordeCAPath: /etc/horde/tls/ca-bundle.pem
```

Omit `grpcPort` in TLS mode: gRPC shares `port` (5000 by default). An explicit
different `grpcPort` is rejected. Use a stable ASCII DNS name covered by the
certificate SAN; URLs, IP literals, wildcards, localhost and trailing dots are
rejected. Set private DNS to the coordinator's private IP.

The coordinator PEM paths must be distinct files in the same dedicated
non-root directory. The key must deny all other-user access and group
write/execute. Give the container process the necessary read access through
your filesystem ownership policy. The directory is mounted read-only, allowing
replacement files at stable paths. The CA bundle must include any additional
roots needed for server outbound integrations.

Trust is configured independently in each environment:

| Environment | Trust |
| --- | --- |
| Coordinator process | Required `tls.caPath`, exposed as `SSL_CERT_FILE` |
| Fabrica CLI | Optional `clientCAPath`; relative paths use the config directory |
| Native agent service | Optional `agents.caPath`, already installed on the agent |
| CodeBuild image | Optional `ci.hordeCAPath`, already installed in the image |
| Browser | Install the issuing CA using your browser/OS policy |

Empty optional CA paths use that environment's system roots. Fabrica does not
copy CA files between machines or store certificate/key bytes in state, user
data or migration output. CLI requests use normal hostname verification, bounded
timeouts and no redirects.

## New coordinator

Generate and bake the Docker AMI. Its base stack has no Horde port publication
and no Horde automatic Docker restart; the gated host unit owns startup.
MongoDB and Redis retain their restart policies. The bake writes
`/etc/horde/fabrica-runtime-contract` containing `1`.

`fabrica horde create` records its connection after SG and instance creation.
First boot installs `/usr/local/sbin/fabrica-horde-bootstrap`, the runtime overlay
and certificate validator. Missing certificate files fail bootstrap until the
operator delivers them using an existing secure SSM workflow. Then retry:

```bash
sudo /usr/local/sbin/fabrica-horde-bootstrap
```

Bootstrap validates the key/certificate pair, SAN, validity, chain and base
stack, then creates/reuses credentials on loopback. It publishes the service
token to the same per-create SecureString, checks TLS-only listeners and HTTP/2,
then exposes the single configured port and sets `bootstrap-complete`. A failed
bootstrap stops Horde. The host unit refuses incomplete bootstrap on reboot.
The bootstrap script is retryable; it retains existing passwords and a pending
token until SSM publication succeeds.

`fabrica horde status` verifies HTTPS and the listener report in TLS mode.
Certificate and listener errors appear in text and JSON. Readiness updates
merge with current state under the account lock. Aggregate `status --probe`
reports TCP reachability explicitly as TLS unverified.

## Native agent AMI

Provide a stock Linux agent with a loaded `horde-agent.service` running as a
non-root user. After verifying that installation, write the AMI contract marker:

```bash
printf '1\n' | sudo tee /etc/horde/fabrica-native-agent-contract
```

Install its optional CA bundle before launch. Cloud-init verifies the marker,
unit and coordinator HTTPS/HTTP2, writes `/etc/horde/fabrica-agent.env`, installs
a systemd `EnvironmentFile` drop-in and restarts the service. It uses the stock
`Horde__Server` and `Horde__ServerProfiles__fabrica__...` settings.

`/etc/horde/agent-configured` means configuration and service start succeeded;
verify actual enrollment and an active Horde session separately. Approval or
your existing registration credential is still required. The CI service token
is never used for agent enrollment.

## Migrate an existing coordinator

Back up configuration and MongoDB before starting. Adoption records only the
coordinator. Existing agent pools and CodeBuild projects with missing/different
transport markers require replacement after coordinator adoption. Drain builds
and preserve agent workspaces according to your policy. Manually modifying a
legacy dependent does not make its recorded contract verified.

1. Pause submitters, CodeBuild schedules and direct project invocations.
   Enable TLS in local config to activate Fabrica's mismatch guard.
2. Prepare private DNS, certificate delivery and trust in all environments.
3. Generate inspectable files:

   ```bash
   fabrica horde tls render --output-dir horde-tls
   ```

   This command loads config locally without initializing a cloud provider.
   Existing output files are refused. Inspect every file before installation.
4. Install over your SSM workflow. Preserve the installed Horde image reference,
   MongoDB named volume, `.env` passwords, Admin account, ACLs and service token.
   Remove Horde `ports`, conflicting transport environment and automatic
   restart from the base Compose file. Install the overlay under `/etc/horde`,
   the validator as `/usr/local/sbin/fabrica-horde-validate` (root-owned and
   executable), and the unit as `/etc/systemd/system/horde.service`.
   Write the base contract marker only after completing those changes.
5. Keep `HORDE_BIND_ADDRESS=127.0.0.1` in `.env`. Validate and start with the
   installed image:

   ```bash
   sudo /usr/local/sbin/fabrica-horde-validate
   sudo docker compose -f /etc/horde/docker-compose.yml \
     -f /etc/horde/fabrica-runtime.json up -d --pull never
   ```

   Use verified curl with `--cacert` and
   `--resolve horde.example.internal:5000:127.0.0.1`. Check existing Admin login,
   the existing service token, HTTPS/HTTP2 and `/api/v1/server/ports`
   (`http=0`, `https=5000`, `unencryptedHttp2=0`). Never run the new-install
   account/database bootstrap during migration.
6. After those checks pass, create `/etc/horde/bootstrap-complete`, set the bind
   to `0.0.0.0`, converge Compose again with `--pull never`, and enable the host
   unit. Recheck browser login and the private-network endpoint. Remove old
   gRPC-only SG ingress using the actual resource IDs from your environment.
7. Adopt the coordinator:

   ```bash
   fabrica horde tls adopt --dry-run
   fabrica horde tls adopt
   ```

   Normal adoption confirms, locks state, inspects the running Docker contract
   over SSM, and verifies HTTPS on the recorded instance's private IP with the
   configured DNS name for SNI and Host. It bypasses proxies for this check.
   Only successful verification writes the coordinator SG/instance records.
   `--yes` skips confirmation; dry runs perform no SSM/HTTPS or lock/state writes.
   Repeating the same adoption safely re-verifies. Failed persistence can be
   retried; there is no downgrade or TLS identity-change flag.
8. Replace the drained stateless dependents with `horde agents destroy/create`
   and `ci destroy/setup` through their normal confirmation flows. Install CI
   trust in the build image first. Verify a real agent session and authenticated
   CodeBuild preflight before resuming submitters and schedules.

The coordinator and its database stay in place throughout this runbook. Do not
edit the S3 state object manually. Restoring an old HTTP config after adoption
fails before credential access.

## Rotation and recovery

For same-CA leaf renewal, replace the certificate and key together using an
operator-managed versioned directory and atomic switch inside the mounted
directory. Retain the configured filenames and DNS identity. Validate, then
explicitly restart only Horde using the installed image:

```bash
sudo /usr/local/sbin/fabrica-horde-validate
sudo systemctl reload horde.service
```

Check HTTPS, browser login and agent reconnection. Reload runs validation and
`docker compose restart --no-deps horde`, without pulling images. This is a
disruptive restart; live certificate reload and zero downtime are not promised.
CA changes require overlapping old/new roots in all trust environments.

`drift --fix` preserves the recorded coordinator transport. A replacement
instance still needs operator-supplied PEM files and updated private DNS; retry
its installed bootstrap after delivery. Export preserves recorded coordinator
SG ports, but omits application runtime overlays, certificate delivery and
TLS bootstrap.

## Runtime smoke checks

Record the exact server image digest/version and stock agent version. Confirm:

- UI login works and the server trusts its own DNS endpoint.
- Authenticated submit succeeds; untrusted CA, wrong SAN and expired leaf fail.
- A real stock agent enrolls and maintains a session using single-port gRPC.
- A real CI build passes listener and authenticated job preflight with image CA trust.
- Port 5002 is closed; HTTP fails on the configured TLS port.
- Same-CA leaf renewal reconnects the agent and preserves MongoDB data,
  existing accounts and service token.

Go tests and generated-file checks do not establish this runtime compatibility.
